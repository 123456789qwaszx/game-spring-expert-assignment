# Lv15. OnlineUsersWsHandler

## 구현 위치

```text
ws/handler/OnlineUsersWsHandler
ws/dto/OnlineUsersResponse
```

## 데이터의 출처

접속자 목록은:

```text
registry.entries(worldId)
```

에서 가져온다.

여기서 중요한 점:

```text
Redis Presence
= 연결이 최근까지 살아 있다고 판단하는 공유 상태

WorldSessionRegistry
= 현재 이 서버가 실제로 가지고 있는 WebSocketSession
```

Lv15는 실제 WebSocket 연결 목록을 응답해야 하므로 Registry가 기준이다.

## 구현 순서

### 1. 현재 World entries

```text
registry.entries(context.worldId())
```

### 2. 열린 연결만 선택

Session이 실제 open인지 확인한다.

닫힌 session은 사용자 목록에서 제외한다.

### 3. nickname 읽기

각 Session의:

```text
NicknameHandshakeInterceptor.ATTR_NICKNAME
```

attribute 사용.

### 4. 정렬

API 명세에서 요구하는 기준으로 nickname 목록을 정렬한다.

임의 기준을 사용하지 않는다.

### 5. 응답

```text
users = 정렬된 nickname 목록
count = users.size()
```

### 6. 전송

```text
broadcaster.sendTo(...)
```

로 요청한 연결에만 응답한다.

접속자 목록 요청을 같은 World 전체에 broadcast하지 않는다.

## 내가 설명할 수 있어야 함

### OnlineUsers는 왜 Redis가 아니라 Registry를 보는가?

이 기능은 "이 서버에 지금 실제로 열려 있는 WebSocket 연결"을 보여주는 기능이기 때문이다.

### Presence와 Session이 불일치할 수 있는가?

가능하다.

네트워크 종료 시점, heartbeat 만료 시점, close 처리 시점이 완전히 같지 않을 수 있다.

그래서 두 시스템은 목적이 다르다.

### 개별 테스트가 다 통과해도 통합 확인이 필요한 이유는?

각 클래스 계약은 정상이어도 실제 순서:

```text
Handshake → Register → Join → Route → Handler → Save/Broadcast
```

에서 연결 문제나 설정 문제가 생길 수 있기 때문이다.
