## 제공 코드 확인

이미 구현:

```text

expiresAt()

```

우리가 구현:

```text

```

## join()

```text
redisTemplate.opsForZSet()
    .add(key, connectionId, expiresAt())
```

그 뒤 제공된 key TTL 갱신 흐름을 유지한다.

## leave()

```text
redisTemplate.opsForZSet()
    .remove(key(worldId), connectionId)
```

## Redis 확인

예:

```text
ZRANGE world:{worldId}:presence 0 -1 WITHSCORES
```

확인:

- member = connectionId
- score = expiry timestamp

# Lv11. PingWsHandler

## 구현 위치

```text
ws/handler/PingWsHandler
```

흐름:

```text
Client ping
    ↓
MessageRouter
    ↓
PingWsHandler
    ↓
presenceService.heartbeat(
    context.worldId(),
    connection.connectionId()
)
    ↓
broadcaster.sendTo(
    context.session(),
    new PongResponse()
)
```

`pong`은 해당 ping을 보낸 연결에만 반환한다.

## heartbeat의 의미

클라이언트는 15초마다 ping을 보낸다.

Presence 만료는 90초다.

따라서 정상 연결:

```text
15초마다 heartbeat
→ expiresAt 갱신
→ 90초 만료 이전에 계속 연장
```

비정상 종료된 연결:

```text
heartbeat 중단
→ expiresAt 도달
→ onlineCount에서 오래된 원소 제거
```

## 내가 설명할 수 있어야 함

### Sorted Set을 Presence에 쓰는 이유는?

member별로 score를 가지므로 connectionId마다 만료 시각을 저장하고,
특정 시각 이전의 만료된 연결을 score 기준으로 제거하기 쉽다.

### 왜 Heartbeat가 필요한가?

정상적인 close 이벤트를 받지 못하는 비정상 종료도 있기 때문이다.

### 왜 Key TTL은 Connection TTL보다 긴가?

각 member의 논리적 만료와 별도로 완전히 사용되지 않는 key 자체를 정리하기 위한 안전장치다.

### Router와 Handler의 책임 차이는?

```text
Router
= type을 보고 담당 Handler 선택

Handler
= 해당 메시지의 실제 기능 수행
```
