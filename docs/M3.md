## 구현 위치

```text
world/service/WorldService
```

이미 제공된 것:

```text
MAX_WORLDS
worldRepository
worldOperations
createPreparedWorld(request)
```

`createPreparedWorld()`는 수정 대상이 아니라 제공 코드로 본다.

## 핵심 문제

잘못된 형태:

```text
A: count = 2
B: count = 2
A: create
B: create
```

두 요청이 동시에 count하면 제한이 3이어도 4개가 될 수 있다.

따라서:

```text
duringCreation(
    count 확인
    → 필요하면 거절
    → create
)
```

전체를 하나의 생성 보호 구간으로 만든다.

## 구현 순서

### 1. `duringCreation()` 계약 확인

- [ ] 어떤 함수형 인터페이스/람다를 받는지 확인
- [ ] 결과값을 어떻게 반환하는지 확인
- [ ] 실제 직렬화 구현은 제공 코드에 맡긴다.

### 2. 람다 내부에서 count

```text
worldRepository.countRootWorlds()
```

### 3. 제한 검사

```text
count >= MAX_WORLDS
```

이면:

```text
ConflictException("WORLD_LIMIT_REACHED")
```

### 4. 생성

제한을 넘지 않으면:

```text
createPreparedWorld(request)
```

결과 반환.

### 5. 기존 제공 로직 보존

`createPreparedWorld()`에는 이미:

- owner 정리
- seed 검증
- player 존재 확인
- seed 결정
- World 저장
- 생성 결과 조립

등이 있으므로 복제하지 않는다.

## 내가 설명할 수 있어야 함

### 왜 count와 create를 그냥 순서대로 호출하면 안 되는가?

각 요청에서는 연속된 코드라도 여러 요청 사이에서는 동시에 실행될 수 있기 때문이다.

### `duringCreation()`의 역할은?

월드 생성의 경쟁 구간을 한 번에 한 요청만 통과시키기 위한 제공 동시성 경계다.

### `@Transactional`만 붙이면 동시 생성 문제가 자동 해결되는가?

아니다.

트랜잭션은 작업의 원자성과 DB 일관성에 중요하지만,
두 트랜잭션이 동시에 같은 count를 읽는 문제를 자동으로 직렬화하지는 않는다.
