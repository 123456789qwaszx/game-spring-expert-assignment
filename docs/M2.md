# M2. 플레이어 등록과 요청 검증 — Lv3

## 목표

API 명세에 맞는 플레이어 등록 요청을 Controller부터 DB 저장까지 완성한다.

닉네임 검증과 중복 처리를 포함하고 성공 시 body 없는 `201 Created`를 반환한다.

## 이번 단계에서 이해할 것

- Controller / Service / Repository
- Request DTO
- Bean Validation
- `@Valid`
- `@RequestBody`
- DB Unique Constraint
- 애플리케이션 사전 중복 검사
- 동시 요청에서의 제약 위반 처리
- `ConflictException`

## API 기준

정확한 경로/메서드/JSON은 API 문서를 다시 확인한 뒤 작성한다.

닉네임 규칙:

```text
비어 있지 않음
2~12글자
영문 대소문자
숫자
_
```

정규식:

```regex
^[a-zA-Z0-9_]+$
```

## 구현 순서

### 1. DTO 검증

`CreatePlayerRequest.nickname`에 요구사항을 표현한다.

확인:

- [ ] blank 금지
- [ ] 2~12자
- [ ] 정규식

DTO는 "유효한 입력이 무엇인지"를 선언한다.

### 2. Controller

확인:

- [ ] API 경로
- [ ] HTTP method
- [ ] `@RequestBody`
- [ ] `@Valid`
- [ ] `playerService.createPlayer(request)`
- [ ] 성공 시 201
- [ ] body 없음

### 3. Service

먼저:

```text
playerRepository.findByNickname(...)
```

또는 제공 Repository 계약으로 중복 여부를 확인한다.

이미 있으면:

```text
ConflictException("DUPLICATE_NICKNAME")
```

### 4. 저장

중복이 아니면 반드시 제공된:

```text
savePlayer(new Player(request.getNickname()))
```

흐름을 사용한다.

`savePlayer()`는 동시 등록에서 발생 가능한 DB unique 제약 위반을 `DUPLICATE_NICKNAME`으로 연결하는 제공 코드다.

### 5. 두 종류의 중복 처리 차이 확인

```text
사전 조회
= 일반적인 중복 요청을 빠르게 거절

DB Unique Constraint
= 동시에 들어온 요청 사이의 최종 무결성 보장
```

## 내가 설명할 수 있어야 함

### DTO에 Validation을 두는 이유는?

외부 입력이 Service/Domain으로 들어오기 전에 API 경계에서 형식을 검증하기 위해서다.

### `@Valid`가 없으면?

DTO 필드에 제약 Annotation이 있어도 Controller parameter validation이 실행되지 않을 수 있다.

### 사전 중복 검사만으로 충분하지 않은 이유는?

두 요청이 동시에 "없음"을 읽고 둘 다 저장할 수 있기 때문이다.

최종적으로 DB의 Unique Constraint가 무결성을 보장해야 한다.

### Entity를 API 응답으로 직접 쓰지 않는 이유는?

Entity는 영속 모델이고 API 계약과 수명이 다르기 때문이다.
API에서는 필요한 필드만 DTO로 노출한다.
