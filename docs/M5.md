# Lv7. 사용자 식별

## 구현 위치

```text
ws/NicknameHandshakeInterceptor
```

연결 주소:

```text
ws://localhost:8080/ws/worlds/{worldId}?nickname={nickname}
```

## 제공 코드 확인

이미 구현:

- nickname query 읽기
- worldId path 읽기
- baseline readiness
- 잘못된 요청 error code
- playerId 저장
- world seed 저장
- difficulty 저장

우리가 작성:

```text
Player 조회
World 조회
ATTR_NICKNAME
ATTR_WORLD_ID
```

## 구현 순서

### 1. Player 조회

```text
playerRepository.findByNickname(nickname)
```

없으면 `null`.

### 2. World 조회

```text
worldRepository.findById(worldId)
```

없으면 `null`.

### 3. 검증 흐름 보존

제공된:

```text
if (player == null) ...
if (world == null ...) ...
```

를 그대로 활용한다.

### 4. Attributes 저장

```text
ATTR_NICKNAME → nickname
ATTR_WORLD_ID → worldId
```

이 정보는 이후:

```text
session.getAttributes()
```

로 사용한다.

## 왜 `putIfAbsent`인가?

잘못된 패턴:

```text
if (!containsKey)
    put
```

두 연산 사이에 다른 Thread가 들어올 수 있다.

`putIfAbsent`는 ConcurrentHashMap이 하나의 원자적 연산으로 처리한다.

## 내가 설명할 수 있어야 함

### 왜 WebSocket 연결 전에 Handshake가 필요한가?

WebSocket도 처음 연결은 HTTP Upgrade 요청에서 시작한다.
이 시점에 연결을 허용하기 전 사용자와 월드를 검증할 수 있다.

### Session Attributes를 쓰는 이유는?

연결할 때 한 번 검증한 정보를 이후 모든 메시지 처리에서 재사용하기 위해서다.

### 왜 nickname을 매 Move/Chat JSON에서 다시 받지 않는가?

클라이언트가 다른 사용자의 nickname을 위조할 수 있기 때문이다.

### SessionRegistry를 Redis에 넣지 않는 이유는?

`WebSocketSession`은 현재 서버 프로세스의 실제 네트워크 연결 객체다.
다른 프로세스에서 그대로 사용할 수 있는 값이 아니다.
