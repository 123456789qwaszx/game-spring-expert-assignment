# M4. 채팅 저장과 최근 채팅 REST API — Lv5 ~ Lv6

## 목표

채팅을 MySQL에 저장하고 월드별 최근 채팅을 REST API로 조회할 수 있게 한다.

M4가 끝나면 WebSocket 실시간 전송은 아직 없어도 된다.
먼저 **채팅의 영속화와 조회 계약**을 완성한다.

## 이번 단계에서 이해할 것

- DTO 변환
- API Controller

- "누가 보냈는가"를 request body가 아니라 서버 연결 정보에서 결정하는 이유

# Lv5. ChatService

## 구현 위치

```text
chat/service/ChatService
```

관련 코드:

```text
ChatMessage
ChatMessageRepository
ChatMessageResponse
ChatSavedEvent
savedResponse(...)
WorldRepository
```

## 구현 순서

### 1. 저장 요청 흐름 확인

메서드:

```text
saveMessage(worldId, sender, content)
```

여기서 sender는 메시지 JSON에서 임의로 받는 값이 아니라
상위 WebSocket 연결에서 확인된 사용자가 전달될 예정이다.

### 2. ChatMessage 생성

현재 Entity 생성자를 확인하고 필요한 값으로 객체를 만든다.

### 3. Repository 저장

반드시:

```text
chatMessageRepository.save(...)
```

사용.

### 4. 저장 응답

반드시 제공된:

```text
savedResponse(worldId, saved)
```

결과를 반환한다.

이 함수는 DTO 생성뿐 아니라 저장 완료 Event 발행도 담당한다.

따라서 응답을 직접 새로 조립해 반환해서 Event를 누락하지 않는다.

### 5. 최근 채팅 조회

제공 코드:

```text
findByWorldIdOrderByCreatedAtDescIdDesc(
    worldId,
    PageRequest.of(0, capped)
)
```

DB 조회 결과는 최신 메시지부터다.

API가 요구하는 반환 순서를 확인하고 필요하면 뒤집어 반환한다.

### 6. DTO 변환

Entity를 그대로 반환하지 않고 `ChatMessageResponse`로 변환한다.

## 내가 설명할 수 있어야 함

### DB 조회는 왜 `createdAt DESC, id DESC`인가?

최근 메시지를 먼저 가져오기 위해 생성 시각 내림차순을 사용하고,
같은 생성 시각이 있을 때도 ID를 이용해 순서를 결정하기 위해서다.

### 왜 저장 후 `savedResponse()`를 사용해야 하는가?

응답 DTO뿐 아니라 채팅 저장 완료 Event를 발행하는 제공 경계이기 때문이다.

### Entity 그대로 반환하지 않는 이유는?

DB 모델과 외부 API 모델을 분리하기 위해서다.

### sender를 메시지 body에서 받으면 무엇이 문제인가?

클라이언트가 다른 사람의 nickname을 넣어 위조할 수 있다.
사용자는 연결 시 검증된 Context에서 결정해야 한다.
