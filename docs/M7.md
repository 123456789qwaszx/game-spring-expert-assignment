# M7. 이동과 실시간 채팅 — Lv12 ~ Lv14

## 목표

게임 클라이언트의 실시간 메시지를 실제 서버 기능으로 연결한다.

- Move → Engine Queue
- Chat → MySQL 저장 → WebSocket Response
- Chat Delivery → 같은 World의 모든 Session으로 Broadcast

M7이 끝나면 실제 두 클라이언트가 같은 월드에서 채팅을 주고받을 수 있어야 한다.

- Connection Context
- Server trust boundary

- Chat persistence
- WS DTO
- Event/Delivery

# Lv12. MoveWsHandler

## 구현 위치

```text
ws/handler/MoveWsHandler
```

## 요청 값 읽기

제공된 `WsFields`를 사용한다.

필드 타입에 따라:

```text
finiteNumber(...)
finiteFloat(...)
booleanValue(...)
```

를 사용한다.

직접 `JsonNode` parsing을 새로 만들지 않는다.

## 신뢰 경계

다음은 request body에서 받지 않는다.

```text
nickname
worldId
```

이미 Handshake에서 검증된 연결 Context를 사용한다.

## PlayerAction.Move

생성자 순서:

```text
nickname
x
y
z
yaw
pitch
crouching
gliding
internal identifier
```

순서를 바꾸지 않는다.

내부 식별자 조회는 제공 코드를 그대로 사용한다.

## Engine enqueue

```text
engineManager.enqueue(
    context.worldId(),
    moveAction
)
```

개념:

```text
WebSocket Handler
= 외부 요청을 게임 엔진이 이해하는 Action으로 번역

Engine
= 실제 게임 상태 처리
```

# Lv13. ChatWsHandler / ChatResponse

## 구현 위치

```text
ws/handler/ChatWsHandler
ws/dto/ChatResponse
```

## readContent()

명세의 content를 읽는다.

가능하면:

```text
WsFields.text(message, fieldName)
```

제공 helper 사용.

## createResponse()

현재 연결 Context:

```text
worldId
nickname
```

을 사용해 Chat 저장 Service 호출.

```text
ChatService
→ MySQL
→ ChatMessageResponse
→ ChatResponse
```

## ChatResponse

API 명세를 기준으로:

- [ ] 필드
- [ ] 타입
- [ ] 생성자
- [ ] JSON 이름

을 정확히 작성한다.

Entity를 그대로 WS로 보내지 않는다.

## 실제 확인

게임에서 일반 채팅 전송:

- [ ] DB에 저장
- [ ] Recent Chat REST에서 조회
- [ ] sender/content/time 확인

Lv13 시점에는 아직 모든 참여자 화면에 broadcast되지 않을 수 있다.

# Lv14. LocalChatSender

## 구현 위치

```text
chat/service/LocalChatSender
```

흐름:

```text
Chat 저장
→ ChatDelivery
→ LocalChatSender.send(worldId, message)
→ WorldBroadcaster.broadcast(worldId, message)
→ 같은 World Session 전체
```

구현은 제공 `WorldBroadcaster`에 위임한다.

```text
worldBroadcaster.broadcast(worldId, message)
```

보낸 사람도 수신 대상이다.

연결별 실패 처리는 `WorldBroadcaster`가 담당하므로 중복 구현하지 않는다.

## world isolation

반드시:

```text
World A의 Chat
→ World A Session만

World B
→ 수신하지 않음
```

이어야 한다.

## 내가 설명할 수 있어야 함

### 왜 Move 요청의 nickname을 body에서 받지 않는가?

서버가 이미 연결 시 사용자를 인증/식별했기 때문이다.
외부 payload에 사용자를 다시 맡기면 다른 사용자로 위장할 수 있다.

### Handler가 직접 게임 상태를 변경하지 않고 enqueue하는 이유는?

WebSocket I/O 처리와 게임 엔진의 상태 변경 경계를 분리하기 위해서다.

### Chat 저장과 Broadcast를 분리한 이유는?

영속화와 전달은 다른 책임이다.

```text
ChatService
= DB 상태

ChatDelivery / Sender / Broadcaster
= 실시간 전달
```

### 왜 LocalChatSender가 Session마다 직접 send하지 않는가?

연결 순회와 개별 전송 실패 정책은 이미 `WorldBroadcaster`가 소유하기 때문이다.
