# M1. 채팅 조회용 JPA 복합 인덱스 — Lv2

## 목표

다음 SQL과 동일한 인덱스가 JPA Entity mapping을 통해 생성되도록 한다.

```sql
CREATE INDEX idx_chat_world_created_at
ON chat_messages(world_id, created_at);
```

직접 SQL로 CREATE INDEX를 실행해서 해결하지 않는다.

## 이번 단계에서 이해할 것

- DB Index
- 복합 Index
- 선두 컬럼
- 컬럼 순서
- JPA `@Table`
- JPA `@Index`
- Java 필드 이름과 실제 DB 컬럼 이름
- Hibernate schema update

## 요구사항

인덱스 이름:

```text

```

컬럼 순서:

```text
world_id, created_at
```

순서를 바꾸지 않는다.

## 구현 순서

### 1. ChatMessage 읽기

- [ ] `@Entity`
- [ ] `@Table`
- [ ] `worldId`가 실제 어떤 컬럼으로 매핑되는지 확인
- [ ] `createdAt` mapping 확인

### 2. 왜 인덱스가 필요한지 먼저 확인

이번 조회는 "한 월드의 최근 채팅"이다.

개념적인 조건:

```sql
WHERE world_id = ?
ORDER BY created_at ...
```

따라서 월드를 먼저 좁히고 생성 시각을 이용하는 인덱스를 둔다.

### 3. JPA Annotation 작성

`@Table(indexes = ...)`와 `@Index(...)`를 사용한다.

확인할 값:

```text
name       = idx_chat_world_created_at
columnList = world_id, created_at
```

### 4. 서버 실행

`ddl-auto=update`가 Entity의 Index 선언을 읽어 실제 DB schema에 반영하게 한다.

### 5. DB 확인

MySQL에서 다음 중 하나로 실제 index를 확인한다.

```sql
SHOW INDEX FROM chat_messages;
```

또는 IntelliJ Database Tool의 table/index 정보를 확인한다.

## 내가 설명할 수 있어야 함

### Index란?

테이블 전체를 처음부터 훑지 않고 특정 조건의 행을 더 빠르게 찾기 위한 별도의 탐색 구조다.

대신 저장 시 index도 함께 갱신해야 하므로 저장 비용과 공간 비용이 생긴다.

### 복합 Index의 컬럼 순서가 왜 중요한가?

```text
(world_id, created_at)
```

과

```text
(created_at, world_id)
```

는 같은 인덱스가 아니다.

어떤 컬럼으로 먼저 데이터를 좁히는지에 따라 활용 가능한 조회 패턴이 달라진다.

### 왜 Java 필드명이 아니라 DB 컬럼명을 쓰는가?

`@Index(columnList=...)`는 실제 테이블 컬럼을 기준으로 인덱스를 선언하기 때문이다.
